# Roadmap ทิศทาง ข: ฟีเจอร์ใช้งานจริง 6 ข้อ

> **For agentic workers:** ไฟล์นี้เป็น roadmap ระดับการออกแบบ ไม่ใช่แผนระดับโค้ด แต่ละฟีเจอร์จะมีแผนละเอียดแยกไฟล์ `docs/superpowers/plans/2026-10-18-<feature>.md` ที่เขียนจาก main ล่าสุดก่อนเริ่มทำฟีเจอร์นั้น ใช้ superpowers:subagent-driven-development ทำทีละ task

**Goal:** เพิ่ม 6 ฟีเจอร์ที่ผู้ใช้ได้ประโยชน์จริง โดยไม่ทำให้ของเดิมพัง

**สถานะ (อัปเดต 2026-10-19):** ข้อ 1 เสร็จและ push แล้ว (รวมไอคอนหมวดและการลบหมวดที่เพิ่มทีหลัง) ข้อ 2 เสร็จและ push แล้ว (รวมคำตอบแบบการ์ด Flex) ข้อ 3 และ 4 เสร็จและ merge เข้า main ในเครื่องแล้ว ยังไม่ push (แผน 2026-10-19-weekly-summary.md, 2026-10-19-daily-reminder.md) ผู้ใช้ตัดสินให้ทำข้อ 3-6 ให้ครบก่อน แล้วรัน SQL `021`-`024` ทีเดียว จากนั้น push ครั้งเดียวหลังข้อ 6 ข้อ 5 เสร็จบน branch feat/savings-goals (แผน 2026-10-19-savings-goals.md) แท็บ ออม เป็นแท็บที่ 6 ของแถบล่าง ยังไม่ merge/push ข้อ 6 ยังไม่เริ่ม เลข migration ของข้อ 2-6 เลื่อนเป็น `020`-`024` เพราะ `018` และ `019` ถูกใช้กับไอคอนหมวดและการลบหมวดแล้ว (ข้อ 2 ใช้ `020` แล้ว ข้อ 3-6 คือ `021`-`024`)

**Architecture:** ตามแบบเดิมของโปรเจกต์ทุกอย่าง: Claude แปลงข้อความเป็น JSON ที่มี schema, ตัวเลขทุกตัวคำนวณด้วย SQL, server กรอง user_id ทุก query, ตารางใหม่เปิด RLS ไม่มี policy (ใช้ผ่าน service role), function SQL ใหม่ revoke จาก public/anon/authenticated แล้ว grant ให้ service_role

**Tech Stack:** Node.js 24 + Express 5, @line/bot-sdk, @anthropic-ai/sdk (claude-haiku-5-5), Supabase Postgres, LIFF (vanilla JS ES modules ใน `public/liff/`), vitest + PGlite

## Global Constraints

- ทำทีละฟีเจอร์ตามลำดับในไฟล์นี้ ห้ามทำขนานกัน (ทุกฟีเจอร์แก้ `src/bot.js`, `src/api/router.js`, `src/db/repository.js`, `public/liff/app.mjs`, `public/liff/index.html`)
- หนึ่งฟีเจอร์ = หนึ่ง branch `feat/<name>` แตกจาก main ล่าสุด, TDD (เขียน test ให้ fail ก่อน), commit ทีละ task, merge เข้า main ในเครื่องด้วย `--no-ff` เมื่อจบฟีเจอร์
- ห้าม `git push`, ห้ามรัน SQL ใน Supabase, ห้ามแก้ `.env`, ห้ามติดตั้งแพ็กเกจใหม่โดยไม่ถาม
- migration ใหม่ต่อเลขจาก `019` (ตอนนี้ไฟล์ล่าสุดคือ `019_delete_category.sql`; 016 ถูกใช้แล้ว revert จึงไม่มีไฟล์ 016) รันซ้ำได้ (`if not exists`, `create or replace`) เพิ่มชื่อไฟล์ใน `MIGRATIONS` ของ `src/db/sql-functions.test.js` และหัวไฟล์ `supabase/schema.sql` และบรรทัด "ไฟล์ล่าสุด" ใน README
- ถ้าโค้ดใหม่ต้องใช้คอลัมน์/ตารางใหม่ตั้งแต่ request แรก README ต้องบอกว่าต้องรัน SQL ก่อน push
- คอมเมนต์ในโค้ดภาษาไทย บรรทัดเดียว อธิบาย "ทำไม" เท่านั้น; ชื่อตัวแปร/function/log ภาษาอังกฤษ; ไม่มี emoji ในโค้ด คอมเมนต์ log commit
- ข้อความที่ผู้ใช้เห็นเป็นภาษาไทย
- push message นับโควตา LINE OA: ฟีเจอร์ที่ push ต้องให้ผู้ใช้เปิดเอง (ค่าตั้งต้นปิด)
- ก่อนจบแต่ละฟีเจอร์: `npm test` และ `npm run lint` ผ่านทั้งหมด, อัปเดต SPEC.md (ฟังก์ชัน, Database, ลำดับการทำ) และ `work-memory/STATE.md`

## 1. หมวดของผู้ใช้เอง (`feat/custom-categories`) -- เสร็จแล้ว

**สิ่งที่ต่างจากการตัดสินใจด้านล่างหลังทำจริง** (รายละเอียดเต็มอยู่ใน SPEC.md ข้อ 9):
- หน้า "หมวดของฉัน" ย้ายจากแท็บโปรไฟล์ไปเป็นหน้าแยก เปิดจากปุ่มล่างสุดของแท็บจัดการงบ (แผน `2026-10-18-category-icons.md`)
- ผู้ใช้เลือกไอคอนหมวดได้ 36 ตัว (`018_category_icon.sql`) แทนที่จะใช้ไอคอน `other` อย่างเดียว
- ลบหมวดได้แล้ว (`019_delete_category.sql`): รายการ รายการประจำ และบิลย้ายไป อื่นๆ งบของหมวดนั้นหายไป หมวดระบบลบไม่ได้ ส่วนการซ่อนยังมีอยู่
- รายการที่พิมพ์แล้ว Claude เลือกหมวดที่ซ่อนอยู่ (กรณีโหลดหมวดไม่ได้) จะลง อื่นๆ ส่วนบิลยังลงหมวดชื่อเดียวกันแม้ซ่อนอยู่

**ผู้ใช้ทำอะไรได้:** ในแท็บโปรไฟล์มีส่วน "หมวดของฉัน" เพิ่มหมวดรายจ่าย/รายรับ, เปลี่ยนชื่อ, ซ่อน/เลิกซ่อน

**การตัดสินใจ:**
- ไม่มีการลบจริง ใช้ "ซ่อน" (`categories.hidden boolean not null default false`) เพราะรายการเก่า งบ รายการประจำ บิล อ้างอิง category_id อยู่ หมวดที่ซ่อนแล้ว: ไม่ส่งให้ Claude เลือก, ไม่ขึ้นในตัวเลือกตอนเพิ่ม/แก้ แต่รายการเก่ายังแสดงชื่อเดิม
- หมวดระบบแก้ไม่ได้ทั้งชื่อและซ่อน: `อื่นๆ` (ทั้งสองประเภท) และ `ใบเสร็จ/สลิปโอนเงิน` เพราะโค้ดอ้างชื่อตรง (`FALLBACK_CATEGORY`, `SLIP_CATEGORY`, `normalizeCategory`, `loadCategoryIds` ซ่อมหมวดเริ่มต้นจากชื่อ)
- หมวดเริ่มต้นอื่น (อาหาร เดินทาง ...) เปลี่ยนชื่อและซ่อนได้ แต่ `users.loadCategoryIds` ปัจจุบันจะ seed หมวดเริ่มต้นกลับมาถ้าชื่อหายไป ต้องเปลี่ยนให้ตรวจเฉพาะหมวดระบบ (`อื่นๆ` x2 และ `ใบเสร็จ/สลิปโอนเงิน`) ไม่งั้นเปลี่ยนชื่อ "อาหาร" แล้วจะมี "อาหาร" งอกกลับมา
- ชื่อหมวด: trim, ยาว 1-30 ตัวอักษร, ห้ามซ้ำในประเภทเดียวกัน (unique เดิม `(user_id, type, name)` ใช้ได้ ตอบ 409), จำนวนหมวดที่ไม่ซ่อนต่อประเภทไม่เกิน 30 (กัน prompt ยาว) และจำนวนหมวดทั้งหมดรวมที่ซ่อนไม่เกิน 100 ต่อผู้ใช้
- parser: `parseMessage(text, history, categories)` รับ `{ expense: string[], income: string[] }` ของผู้ใช้ (ไม่รวมที่ซ่อนและไม่รวมหมวดสลิป) แล้วสร้าง enum ใน schema และ prompt ต่อ request; `normalizeCategory` รับรายการหมวดเป็นพารามิเตอร์แทนค่าคงที่ ถ้าโหลดหมวดไม่ได้ใช้ `TEXT_CATEGORIES` เดิมเป็นค่าตั้งต้น
- LIFF ไอคอน: หมวดที่ไม่อยู่ใน `CATEGORY_KEYS` ใช้ไอคอน `other` อยู่แล้ว ไม่ต้องเพิ่มระบบเลือกไอคอน (YAGNI); แต่หมวดเริ่มต้นที่เปลี่ยนชื่อจะเสียไอคอนเดิม ยอมรับได้ในเฟสนี้
- API ใหม่: `POST /api/categories` `{ type, name }` -> 201 `{ category: { id, name, type, hidden, system } }`; `PATCH /api/categories/:id` `{ name? , hidden? }` -> 200 `{ category }`; `GET /api/categories` เดิมคืน `hidden` และ `system` เพิ่ม
- migration `017_category_hidden.sql`

## 2. ถามยอดด้วยภาษาธรรมชาติ (`feat/ask-totals`)

**ผู้ใช้ทำอะไรได้:** พิมพ์ "เดือนนี้กินกาแฟไปเท่าไหร่", "ค่าเดินทางเดือนที่แล้ว", "สัปดาห์นี้ใช้ไปเท่าไร" แล้วบอทตอบยอดรวมกับจำนวนรายการ

**การตัดสินใจ:**
- ไม่แตะ parser หลัก แยก module `src/query/` เพื่อไม่ให้ความเสี่ยงไปถึงการบันทึกรายการ
- ประตูก่อนเรียก Claude: `looksLikeQuestion(text)` ด้วย regex คำถาม (`เท่าไหร่|เท่าไร|กี่บาท|ไปเท่า|ใช้ไปเท่า|รวมเท่า`) และ**ไม่มี**ตัวเลขจำนวนเงินในข้อความ; ผ่านประตูแล้วเรียก `parseQuestion(text, categories)` ด้วย json_schema: `{ is_question, type: expense|income|both, category: <enum ของผู้ใช้> | "", keyword: string, from: YYYY-MM-DD, to: YYYY-MM-DD }` ถ้า `is_question` เป็น false ให้ไปทาง parser บันทึกรายการตามเดิม
- ยอดคำนวณด้วย SQL function ใหม่ `query_totals(p_user_id, p_from, p_to, p_type, p_category_id, p_keyword)` คืน `type, total, entry_count` (keyword ค้นใน note ด้วย `ilike` และ escape `%` `_`)
- ช่วงวันที่: Claude คืน from/to; server ตรวจว่าเป็นวันที่จริง, from <= to, ช่วงไม่เกิน 366 วัน; ถ้าไม่ผ่านใช้เดือนนี้
- นับ rate limit เหมือนข้อความที่เรียก Claude อื่น; claimEvent ก่อนเหมือนเดิม
- คำตอบเป็นข้อความธรรมดา เช่น `ช่วง 1-18 ต.ค. 2569 หมวด อาหาร คำว่า "กาแฟ": รายจ่าย 450 บาท (6 รายการ)` ใช้ `formatAmount` เดิม และวันที่แบบที่ summary ใช้
- migration `020_query_totals.sql`

## 3. สรุปรายสัปดาห์ (`feat/weekly-summary`)

**ผู้ใช้ทำอะไรได้:** เปิดสวิตช์ "ส่งสรุปทุกวันอาทิตย์" ในแท็บโปรไฟล์ แล้วทุกวันอาทิตย์ 19:00 บอทส่งการ์ดสรุปสัปดาห์นั้น (จันทร์-อาทิตย์)

**การตัดสินใจ:**
- ตั้งค่าเก็บในตาราง `users`: `weekly_summary_enabled boolean not null default false` (ข้อ 6 เพิ่ม `daily_reminder_enabled` ในตารางเดียวกัน)
- API: `GET /api/settings` -> `{ weeklySummary, dailyReminder }` (ข้อ 6 เติม field), `PATCH /api/settings` รับ boolean เฉพาะ field ที่รู้จัก
- กันส่งซ้ำ: ตาราง `notification_log (user_id, kind text, period text, created_at, primary key (user_id, kind, period))` จอง (insert on conflict do nothing) ก่อน push; period ของสรุปรายสัปดาห์ = วันจันทร์ของสัปดาห์ (YYYY-MM-DD)
- endpoint cron `POST /internal/notifications/weekly` ป้องกันด้วย `CRON_SECRET` ตัวเดิม ทำแบบเดียวกับ `src/recurring/router.js` (แยก helper `safeEqual`/ตรวจ bearer ไปไว้ที่เดียวแล้วใช้ร่วมกัน)
- การ์ดใช้ `buildSummary` + `buildSummaryFlex` เดิม ช่วง `week`; **ไม่เรียก Claude เขียนคอมเมนต์** (คุมเวลาให้ทัน timeout 30 วินาทีของ cron-job.org และคุมค่าใช้จ่าย) ส่งคอมเมนต์ว่าง; สัปดาห์ที่ไม่มีรายการเลยไม่ส่ง (ไม่เสียโควตา)
- ส่ง push ทีละคนต่อกัน, push พังของคนหนึ่งไม่หยุดคนอื่น, คืน `{ eligible, sent, skipped, failed }` และตอบ 500 ถ้า failed > 0 เหมือน recurring
- เพิ่ม `pushFlex` ให้ runner (มีใน `src/line-reply.js` แล้ว)
- ผู้ใช้ต้องเพิ่มงานใน cron-job.org: `POST <URL>/internal/notifications/weekly` ทุกวันอาทิตย์ 19:00 (Asia/Bangkok) พร้อม header Authorization เดียวกับ recurring; ใส่ใน README
- migration `021_notification_settings.sql` (คอลัมน์ทั้งสองตัวของข้อ 3 และ 6 + ตาราง notification_log สร้างครั้งเดียวที่นี่)

## 4. เตือนลืมจด (`feat/daily-reminder`)

**ผู้ใช้ทำอะไรได้:** เปิดสวิตช์ "เตือนถ้าวันนี้ยังไม่ได้จด" แล้วถ้าถึง 21:00 วันนั้นยังไม่มีรายการที่ผู้ใช้จดเอง บอทส่งข้อความเตือนสั้นๆ

**การตัดสินใจ:**
- "จดเอง" = transactions ที่ `source in ('text','slip')` และ `created_at` อยู่ในวันนี้ตามเวลา Asia/Bangkok (ไม่นับรายการประจำและบิลที่ระบบใส่ให้) ใช้ SQL function `users_to_remind(p_day date)` คืน `user_id, line_user_id` ของคนที่เปิดสวิตช์และยังไม่มีรายการ
- กันส่งซ้ำด้วย `notification_log` kind `daily_reminder` period = วันนี้
- endpoint `POST /internal/notifications/daily-reminder` ใช้ helper ตรวจ secret เดียวกับข้อ 3
- ข้อความ: `วันนี้ยังไม่ได้จดรายการเลย ใช้อะไรไปบ้าง พิมพ์มาได้เลย เช่น "กินข้าว 60"` ไม่มีปุ่ม
- ผู้ใช้ต้องเพิ่มงาน cron-job.org ทุกวัน 21:00
- migration `022_daily_reminder.sql` (เฉพาะ function; คอลัมน์และตารางมีจากข้อ 3 แล้ว)

## 5. เป้าหมายการออม (`feat/savings-goals`)

**ผู้ใช้ทำอะไรได้:** สร้างเป้า (ชื่อ ยอดเป้า วันที่อยากถึงเป้า ไม่บังคับ), ออมเข้าเป้าจาก LIFF หรือพิมพ์ในแชท `ออม เที่ยวญี่ปุ่น 1000`, ดูหลอดความคืบหน้า, ลบรายการออมที่ใส่ผิด, ปิดเป้า

**การตัดสินใจ:**
- แยกจาก transactions ทั้งหมด: ยอดออมไม่ใช่รายจ่ายและไม่กระทบ "ยอดคงเหลือสะสม" เดิม
- ตาราง `savings_goals (id, user_id, name, target_amount numeric(12,2) > 0, target_date date null, closed boolean default false, created_at, unique (user_id, name))` และ `goal_contributions (id, goal_id, user_id, amount numeric(12,2) > 0, occurred_on date, line_event_id text null, created_at)` FK `(goal_id, user_id)` ไปยัง goals กันใส่ข้ามผู้ใช้; ยอดสะสมคำนวณด้วย SQL (`sum` ผ่าน view หรือ function `goal_progress(p_user_id)`)
- เฟสนี้ไม่มี "ถอน" (YAGNI) แก้ผิดด้วยการลบรายการออม
- คำสั่งในแชทไม่ใช้ Claude: regex `^ออม\s*(.+?)\s+([\d,]+(?:\.\d{1,2})?)\s*(?:บาท)?$` จับชื่อเป้าแบบตรงตัว (trim, ไม่สนตัวพิมพ์); ไม่เจอเป้าตอบรายชื่อเป้าที่เปิดอยู่; ทำก่อน fixed replies และไม่นับ rate limit; claimEvent ก่อนเหมือนข้อความอื่น; ตอบพร้อมปุ่ม "ยกเลิก" ที่ลบรายการออมนั้น (postback action ใหม่ `undo_saving`)
- LIFF: แท็บใหม่ "ออม" (id `goals`, ไอคอนใหม่ `tab-goal`) ใน `TABS` ของ `public/liff/tabs.mjs`
- API: `GET/POST /api/goals`, `PATCH /api/goals/:id` (ชื่อ ยอดเป้า วันที่ closed), `POST /api/goals/:id/contributions`, `GET /api/goals/:id/contributions`, `DELETE /api/goals/:id/contributions/:contributionId`
- migration `023_savings_goals.sql`

## 6. กระเป๋าเงิน เฟส 1 (`feat/wallets`)

**ผู้ใช้ทำอะไรได้:** มีกระเป๋า "เงินสด" ให้ตั้งแต่แรก สร้างกระเป๋าเพิ่ม (เช่น บัตรเครดิต, กสิกร) ในแท็บโปรไฟล์, ทุกรายการมีกระเป๋า, พิมพ์ "กาแฟ 60 รูดบัตร" แล้ว Claude เลือกกระเป๋าให้, แก้กระเป๋าของรายการใน LIFF, ดูยอดแยกกระเป๋าในโปรไฟล์ และกรองรายการตามกระเป๋า

**การตัดสินใจ:**
- ตาราง `wallets (id, user_id, name, hidden boolean default false, created_at, unique (user_id, name), unique (id, user_id))`; `transactions.wallet_id uuid null` FK `(wallet_id, user_id)` -> wallets; รายการที่ wallet_id เป็น null แสดงเป็นกระเป๋าตั้งต้น (ไม่ backfill รายการเก่าทั้งตารางใน migration เพื่อลดความเสี่ยงล็อกตาราง) -- `lifetime_totals` แยกกระเป๋าด้วย function ใหม่ `wallet_totals(p_user_id)` ที่นับ null เป็นกระเป๋าตั้งต้น
- กระเป๋าตั้งต้นชื่อ "เงินสด" สร้างตอนสมัคร (เหมือน seedDefaultCategories) และซ่อมใน `loadWalletIds` ถ้าหาย; เปลี่ยนชื่อไม่ได้ ซ่อนไม่ได้
- parser: เพิ่ม field `wallet` ใน item (enum ชื่อกระเป๋าของผู้ใช้ + `""`); `""` หรือไม่รู้จัก = กระเป๋าตั้งต้น; ถ้าผู้ใช้มีแค่กระเป๋าเดียวไม่ต้องส่ง field นี้ใน prompt (ประหยัด token) แต่ schema ยังมีได้
- สลิป รายการประจำ บิล: ใช้กระเป๋าตั้งต้น (null) เฟสนี้ไม่ให้เลือก
- ไม่มีโอนระหว่างกระเป๋า ไม่มียอดยกมา (opening balance) ในเฟสนี้
- ถามยอด (ข้อ 2): เพิ่ม `wallet` ใน schema ของคำถามและ parameter `p_wallet_id` ใน `query_totals` (create or replace)
- API: `GET/POST /api/wallets`, `PATCH /api/wallets/:id`; `PATCH /api/transactions/:id` รับ `walletId`; `GET /api/transactions` คืน `walletId`/`walletName`
- migration `024_wallets.sql`
